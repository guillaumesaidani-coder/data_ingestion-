Section 1 — Optuna

Espace de recherche des hyperparamètres

Les hyperparamètres sont choisis selon leur impact sur l'overfitting diagnostiqué en TP7. Optuna (TPE) explore intelligemment cet espace : chaque trial informe les suivants.

Paramètre Plage Rôle — pourquoi cet intervalle
max_depthanti-overfit [2, 6] Profondeur max des arbres. Réduire de 6 vers 3–4 simplifie les décisions et diminue la mémorisation du train.
min_child_weightanti-overfit [1, 20] Nombre min d'observations par feuille. Augmenter de 1 vers 5–10 évite les feuilles sur-spécialisées.
reg_alpha (L1)anti-overfit [0, 2] Régularisation L1 : pousse les poids de features peu utiles vers zéro. Baseline = 0 (aucune pénalité).
reg_lambda (L2)anti-overfit [1, 10] Régularisation L2 : lisse les poids. Augmenter de 1 vers 5–10 réduit la variance du modèle.
n_estimators [100, 500] Nombre d'arbres. Plus d'arbres = plus de capacité, mais aussi plus de risque de surapprentissage sans régularisation.
learning_ratelog-scale [0.01, 0.3] Pas d'apprentissage. Exploration log-scale : 0.01 (lent) à 0.3 (agressif). Baseline = 0.1.
subsample [0.6, 1.0] Fraction des observations utilisées par arbre. Sous-échantillonner réduit la corrélation entre arbres.
colsample_bytree [0.5, 1.0] Fraction des features par arbre. Moins de features par arbre = plus de diversité dans l'ensemble.
objective = maximize PR-AUC val sampler = TPE(seed=42) # Tree-structured Parzen Estimator study = optuna.create_study(direction="maximize", sampler=sampler) study.optimize(objective, n_trials=60)

Section 2 — Explicabilité

SHAP — au-delà de feature_importances_

feature_importances_ (gain XGBoost) biaise les scores vers les features à haute cardinalité. SHAP calcule la contribution marginale de chaque feature pour chaque prédiction individuelle.

Concept
Valeur de Shapley
Issue de la théorie des jeux coopératifs. Mesure la contribution marginale d'un joueur (feature) à la prédiction, en moyennant sur toutes les coalitions possibles.
Signe
Direction de l'impact
SHAP > 0 → la feature pousse la prédiction vers "panne". SHAP < 0 → vers "pas de panne". Le summary plot montre les deux dimensions à la fois.
Globalité
mean |SHAP|
La moyenne des valeurs absolues donne l'importance globale — comparable à feature_importances_ mais sans le biais cardinalité. On la calcule sur 2 000 exemples train.
Outil
TreeExplainer
Version optimisée de SHAP pour les modèles à base d'arbres (XGBoost, RandomForest). Complexité O(TLD²) — très rapide par rapport à KernelExplainer.
Avant — TP7
feature_importances_ (gain)
  • Biaisé vers les features à nombreuses valeurs distinctes
  • Agrège sur tout le train — pas d'info par prédiction
  • Donne une seule valeur positive — pas de direction
  • incident_max_severity_prev_24h = 63 % du signal total
Après — TP8
SHAP (TreeExplainer)
  • Non biaisé par la cardinalité
  • Une valeur SHAP par feature par observation
  • Direction + intensité de l'impact
  • Vérifie si la sur-dépendance à incident reste après optimisation

Section 3 — Analyse critique

Deux alertes à instruire — fuite ou signal ?

Toute feature avec une importance très élevée et tout recall élevé méritent d'être questionnés. Ce n'est pas systématiquement une erreur — mais ça doit se démontrer, pas se supposer.

Alerte 1 — Feature importance
incident_max_severity_prev_24h = 63 % de l'importance
Deux types de fuite possibles
Type A — Fuite temporelle ✅ Écarté La fenêtre est définie avec occurred_at < h (strict) dans TP6 cell [16]. Les fenêtres prev_24h et next_24h sont disjointes par construction.
Type B — Signal réactif ⚠️ Confirmé — Δ ablation = 0.170 Ablation §7b : PR-AUC 0.862 → 0.691 sans la feature. Le modèle dépend quasi-exclusivement de ce signal. La feature reste légitime (fenêtres disjointes) mais réactive : elle encode "la machine vient d'avoir un incident" plutôt qu'une anticipation physique. Piste : enrichir les features télémétriques (température, vibration, pression) pour réduire cette dépendance.
Test à exécuter dans le notebook

Section 4 — Seuil de décision

Quel seuil choisir ?

Trois critères objectifs. Le critère Recall ≥ 90 % est retenu car FN coûte 33× plus que FP dans ce contexte industriel.

Critère 1
F1 maximum
argmax 2·P·R / (P + R)
Quand le coût des fausses alarmes et des pannes manquées est comparable. Pas notre cas.
Non retenu
Critère 2 — retenu
Recall ≥ 90 %
min seuil tel que R ≥ 0.90
Garantit de détecter au moins 90 % des vraies pannes. Correspond au ratio de coût FN/FP ≈ 33×.
Retenu
Critère 3
Coût total minimum
argmin FN·5 000 + FP·150
Optimal si les coûts unitaires sont calibrés avec précision par l'équipe métier. Alternative rigoureuse.
Alternative
precision, recall, thresholds = precision_recall_curve(y_val, y_proba) # Seuil Recall >= 90% idx_r90 = np.where(recall[:-1] >= 0.90)[0] seuil_retenu = thresholds[idx_r90[-1]] # Appliquer en production y_pred = (y_proba >= seuil_retenu).astype(int)

Pourquoi XGBoost sur ce problème ?
Le déséquilibre de classes (3.6 % positifs) est la contrainte principale. XGBoost le gère directement via scale_pos_weight=27 — le modèle pondère les pannes 27× plus que les cas normaux pendant l'entraînement. Random Forest n'a pas d'équivalent natif : il faut recourir à class_weight ou du suréchantillonnage (SMOTE), ce qui dégrade souvent la calibration des probabilités. C'est pour cette raison que l'autre étudiant, dont le RF retient un seuil de 0.083, doit abaisser drastiquement son seuil pour compenser — là où XGBoost optimisé maintient un bon recall à seuil 0.84.
