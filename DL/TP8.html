§1 Le principe : un template, pas une invention

Une model card répond, sur une page, à : que fait ce modèle, sur quelles données, avec quelle performance, dans quelles limites, et comment l'utiliser ? Plutôt qu'un format maison, on remplit le template standard Hugging Face (huggingface_hub.ModelCard.from_template) — reconnu, structuré, avec usage, données, métriques, limites et impact déjà prévus.

from huggingface_hub import ModelCard, ModelCardData

card_data = ModelCardData(model_name=..., license=..., tags=[...], eval_results=[...])
card = ModelCard.from_template(card_data, **template_kwargs)  # 45 champs {{ }}
card.validate()   # conformité du front-matter YAML
card.save("model_card.md")
Méthode identique dans les deux cas : recharger/reconstruire le modèle et recalculer les métriques en direct — jamais recopier un chiffre d'un ancien run non vérifiable. Les deux notebooks (DL/TP8.ipynb, ML/model_card.ipynb) confirment que leurs métriques recalculées sont strictement identiques à celles déjà documentées ailleurs (TP4 pour le DL, TP11 pour le ML).

Le vrai test d'une model card n'est pas de couvrir tous les champs du template — c'est de documenter ce qui rendrait un lecteur méfiant : un modèle moins bon qu'une alternative connue, un historique de fuite, une performance qui s'effondre sur un sous-groupe. Une card qui ne dit que du bien du modèle qu'elle documente a raté son objet.
