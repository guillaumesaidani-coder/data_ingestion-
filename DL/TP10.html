§1 Point de départ : ce qui a été construit

Pour produire les deux model cards, deux notebooks avaient été écrits — même schéma dans les deux cas : recharger/ré-entraîner le modèle, recalculer les métriques en direct, instrumenter CodeCarbon, interroger MLflow, puis appeler ModelCard.from_template(...) et sauvegarder un .md.

§2 Le diagnostic : deux couches confondues

Une model card répond à « que fait ce modèle, avec quelle performance, dans quelles limites » — c'est un document, lu par un humain, pas exécuté.

Document

model_card.md — texte, tableaux, prose. Se lit, se diffuse, se versionne comme du texte pur.

Ce qui a été fait à tort

Le document relégué en sous-produit, généré en dernière cellule d'un notebook Jupyter — le nom du fichier ML affirmait même être la card.

Processus (légitimement scriptable)

Recharger le modèle, recalculer les métriques, interroger MLflow — un script .py suffit, pas un notebook.

Le signal le plus clair : le nom du fichier. model_card.ipynb affirme, par son nom, qu'il est la card. Un notebook ne peut pas être une documentation — il peut au mieux la produire. Conséquence visible : la première version de TP8.html disait littéralement « Les deux notebooks (DL/TP8.ipynb, ML/model_card.ipynb) confirment que... » — la page pédagogique elle-même comparait des pipelines d'exécution, pas des documents de référence.

Ce qui disparaît

  • Le kernel Jupyter et son cycle exécution/sortie capturée (nbconvert --execute)
  • L'ambiguïté « le fichier .ipynb est-il le document ou l'outil ? »
  • Le risque qu'une exécution partielle (cellules dans le désordre) laisse le .md incohérent avec le code qui l'a produit

Ce qui reste identique

  • La règle ne jamais copier un chiffre — les scripts recalculent les métriques en direct à chaque exécution
  • La sortie : DL/reports/model_card.md et ML/artifacts/model_card.md, mêmes chemins, même rôle

§5 Ce qui reste légitimement un notebook

Tous les notebooks ne sont pas suspects — seuls ceux qui sont nommés ou traités comme un document le sont. DL/TP9.ipynb (tracking MLflow de B11-GKF) reste un notebook à raison.

Critèremodel_card.ipynb (supprimé)TP9.ipynb (conservé)
ObjetÊtre lu comme documentationRé-entraîner, logger, vérifier une action
NomAffirme être « la card »Convention TPx — une étape numérotée

Le critère qui tranche. Si le fichier est destiné à être lu seul, hors contexte d'exécution, par quelqu'un qui ne l'exécutera jamais — c'est un document, il doit être .md. Si son rôle est de vérifier, calculer ou orchestrer une action ponctuelle — un notebook (ou un script) convient.
