02 — Principe

Comment fonctionne l'auto-encodeur ?

On entraîne le modèle à compresser puis reconstruire uniquement des pièces saines. Une fois entraîné, il ne sait reconstruire que ce qu'il a vu — c'est-à-dire le normal. Quand on lui présente un défaut, la reconstruction est mauvaise : l'erreur de reconstruction devient le score d'anomalie.

Insight clé
L'auto-encodeur ne peut reconstruire que ce qu'il a appris à reconstruire : des pièces saines. Présenté à un défaut, il le reconstruit "corrigé" → l'erreur pixel révèle la zone anormale.

04 — Étape 1

Chargement, normalisation et split

Pourquoi normaliser dans [0, 1] ?

Les pixels bruts sont en [0, 255] (uint8). Diviser par 255 les place dans [0, 1] en float32 — ce que les couches de convolution et la fonction d'activation sigmoïde du décodeur attendent.

Split train / val

On réserve 20 % des images saines pour la validation, avec un tirage aléatoire fixe (seed=42). Résultat : 168 images train, 41 images val. La validation servira à calibrer le seuil en partie 2 — elle ne doit pas voir d'images défectueuses.

from indusense.vision.dataset import load_train_val, load_test

# Split reproductible : 80 % train / 20 % val
X_train, X_val = load_train_val(BOTTLE_ROOT, val_ratio=0.2, seed=42)
X_test, y_test, classes = load_test(BOTTLE_ROOT)

# X_train : (168, 256, 256, 3) float32  — valeurs dans [0, 1]
# X_val   : (41,  256, 256, 3) float32
# X_test  : (83,  256, 256, 3)  y_test : 0=saine / 1=défaut
Règle importante
Les images de validation et de test ne sont jamais augmentées. L'augmentation s'applique uniquement à X_train pendant l'entraînement.
05 — Étape 2

Normalisation des pixels

Deux étapes complémentaires permettent de mettre tous les pixels à la même échelle avant d'entrer dans le réseau.

Étape 1 — déjà faite au chargement
Mise à l'échelle [0, 1]

Division par 255 : les uint8 [0–255] deviennent des float32 [0–1]. La sigmoïde du décodeur produit des valeurs dans [0, 1] — la MSE est cohérente.

X = pixel / 255.0
Étape 2 — standardisation
Centrage-réduction par canal

Centre chaque canal R/G/B autour de 0 avec σ=1. Stabilise le gradient et accélère la convergence de l'optimiseur.

X = (X − μ) / σ

Règle anti-fuite — stats train uniquement

μ et σ sont calculés sur X_train exclusivement, puis appliqués à val et test sans recalcul. Utiliser les stats de val ou test reviendrait à laisser filtrer de l'information du futur dans le modèle (data leakage).

from indusense.vision.dataset import compute_stats, standardize

# Stats calculées sur le train uniquement
mean, std = compute_stats(X_train)
print(mean)   # ex. [0.4812, 0.4721, 0.4689]  — par canal RGB

# Même mean/std appliqués partout
X_train = standardize(X_train, mean, std)
X_val   = standardize(X_val,   mean, std)
X_test  = standardize(X_test,  mean, std)
Pourquoi par canal et pas globalement ?
Les trois canaux R/G/B d'une image de bouteille ont des distributions légèrement différentes (le verre réfléchit la lumière différemment selon la longueur d'onde). Standardiser canal par canal évite que l'un d'eux domine la reconstruction.
06 — Étape 3

Pipeline d'augmentation (Albumentations)

L'augmentation artificialise la variabilité des données saines pour empêcher l'auto-encodeur de mémoriser exactement les 168 images d'entraînement. Elle doit élargir la notion de "normal" sans la dénaturer.

✓ Retenues pour bottle
✓ Retenu · p=0.50
HorizontalFlip
La bouteille est symétrique gauche/droite — une bouteille vue en miroir reste une bouteille saine.
✓ Retenu · p=0.70
Rotate(limit=15°)
Légère inclinaison de pose caméra ou de placement sur le convoyeur. Au-delà de 30° la bouteille sort du cadre.
✓ Retenu · p=0.70
RandomBrightnessContrast
Variation d'éclairage industriel entre sessions (±15 %) — très fréquente en production réelle.
✓ Retenu · p=0.50
HueSaturationValue
Léger drift de teinte entre lots de production (verre légèrement teinté). Amplitudes conservatrices.
✓ Retenu · p=0.30
GaussNoise
Simule le bruit capteur de la caméra industrielle. Probabilité basse pour ne pas bruiter le signal utile.
✗ Écartées
✗ Écarté
VerticalFlip
Une bouteille retournée tête en bas n'est pas "normale" — le modèle apprendrait à tolérer ce cas.
✗ Écarté
ElasticTransform
Déformation irréaliste sur un objet rigide en verre. Risque de rendre le modèle tolérant à des défauts de forme.
✗ Écarté
RandomCrop / Zoom fort
Couper la bouteille produit des images hors-distribution — le modèle apprendrait à reconstruire des demi-bouteilles.
07 — Point de réflexion

Objet centré vs Texture — une stratégie différente

Le bon choix d'augmentation dépend de la nature de l'objet, pas du dataset en général. La même transform peut être excellente pour une texture et catastrophique pour un objet.

🍾 bottle — Objet centré

La bouteille est orientée, centrée, alignée dans l'image. Chaque transformation géométrique forte élargit la notion de "normal" vers des configurations irréelles.

HorizontalFlip ✓ Rotate ±15° ✓ VerticalFlip ✗ Rotation 90° ✗ Elastic ✗

Stratégie : conservatrice — favorise la sensibilité aux anomalies.

🔲 tile — Texture isotrope

Le carrelage est uniforme dans toutes les directions. N'importe quelle rotation ou flip produit une image réaliste — la texture n'a pas de "haut" ou de "bas".

HorizontalFlip ✓ VerticalFlip ✓ Rotation 90° ✓ RandomCrop ✓ Elastic ✓

Stratégie : agressive — la texture supporte toutes les transformations géométriques.

08 — Bonnes pratiques

Versionnage du dataset

Un dataset non versionné n'est pas reproductible. Si les images changent, si le split change ou si les stats de normalisation changent, le modèle entraîné n'est plus le même — sans qu'on le sache.

Pourquoi versionner ?

Reproductibilité

Le même identifiant de version produit toujours le même dataset, même 6 mois plus tard.

Traçabilité

On sait exactement quelles images, quel split et quelles stats ont produit un modèle donné.

Collaboration

Un coéquipier peut recréer le dataset sans poser de questions.

Retour arrière

Si un nouveau split dégrade les performances, on peut revenir à la version précédente.

Ce qui est versionné dans ce projet

from indusense.vision.dataset import save_stats, load_stats

# Après compute_stats — sauvegarder dans un fichier commité dans Git
save_stats(mean_train, std_train, path="norm_stats.json")

# En inférence (ou pour un collaborateur) : recharger sans recalculer
mean, std = load_stats("norm_stats.json")
img_standardized = standardize(img_new, mean, std)
Règle d'or
Un même version_id dans dataset_card.yaml + le même dataset.py doivent toujours produire le même dataset — mêmes images, même split, mêmes stats.

Pour aller plus loin

DVC (Data Version Control) étend Git pour versionner de gros fichiers binaires (images, modèles) en stockant leur hash dans Git et le contenu dans un remote (S3, GCS…). Git-LFS fait de même directement dans GitHub. Pour ce TP, l'approche légère (dataset_card.yaml + norm_stats.json + .gitignore) suffit.
