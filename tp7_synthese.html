Le problème

Classification binaire sous contraintes industrielles

⚙️

Cible binaire

Pour chaque machine et chaque heure, le modèle prédit si une panne critique (sévérité ≥ 4) surviendra dans les 24 prochaines heures.

label_failure_next_24h
⚖️

Déséquilibre de classes

Les pannes sont rares : seulement ~3,6 % d'observations positives. L'accuracy est inutile — un modèle prédisant toujours 0 afficherait 96,4 %.

Utiliser PR-AUC
⏱️

Fuite temporelle

Un split aléatoire laisserait des données futures dans le train. On impose un split temporel strict : train < validation < test.

Split 70 / 15 / 15

Entraînement

Trois modèles, du plus simple au plus expressif

Modèle 01
Régression Logistique
Linéaire · Baseline

Combine linéairement les 78 features via une fonction sigmoïde. Nécessite une standardisation. Rapide, interprétable, révèle si le problème est linéairement séparable.

max_iter1000
solver"lbfgs"
PipelineImputer → Scaler → LR
Modèle 02
Random Forest
Ensemble · Non linéaire

Vote de 200 arbres entraînés sur sous-échantillons aléatoires. Capture les interactions non linéaires. Robuste aux outliers — pas besoin de standardisation.

n_estimators200
max_depth10
class_weight"balanced"
n_jobs-1
Modèle 03
XGBoost
Gradient Boosting · Candidat principal

Arbres construits séquentiellement : chaque arbre corrige les erreurs du précédent. Régularisation intégrée, gestion native des NaN, meilleur sur données tabulaires.

n_estimators300
max_depth6
learning_rate0.1
scale_pos_weightneg / pos

Lecture et arbitrage métier

Vrai Positif — la bonne alerte

La machine allait tomber en panne, le modèle l'a prédit. L'équipe peut intervenir en avance.

Faux Négatif — la panne manquée ❌ Coûteux

Le modèle prédit "tout va bien" alors qu'une panne survient. Coût élevé : arrêt non anticipé, production perdue.

Faux Positif — la fausse alerte

Intervention préventive inutile, mais sans danger. En contexte industriel, on tolère plus de fausses alertes que de pannes manquées.

Seuil de décision — levier d'action

Baisser le seuil (0.3) augmente le Recall (moins de pannes manquées) au prix de plus de fausses alertes.

Métrique principale

PR-AUC plutôt qu'accuracy — les classes sont déséquilibrées (3,6 % positifs).

Split

Temporel strict (70/15/15) via split_set — jamais aléatoire pour éviter la fuite temporelle.

Déséquilibre

class_weight="balanced" (LR/RF) et scale_pos_weight = neg/pos (XGBoost).
