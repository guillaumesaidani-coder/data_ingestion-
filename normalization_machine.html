01

Le problème — Baselines machine hétérogènes

Chaque machine a ses propres valeurs nominales. Une pression de 205 bar peut être normale pour MACH-07 et anormale pour MACH-01. Sans normalisation, le modèle apprend des niveaux absolus plutôt que des déviations par rapport à la normale de chaque machine.

# Sans normalisation — le modèle confond baselines et anomalies
MACH-01 : pressure_mean = 195  (normal)  → label = 0
MACH-07 : pressure_mean = 205  (normal)  → label = 0
MACH-01 : pressure_mean = 205  (anomalie) → label = 1  ← ambigu

# Avec z-score par machine — le signal devient universel
MACH-01 : z = (195 - µ_01) / σ_01 = 0.0  → label = 0
MACH-07 : z = (205 - µ_07) / σ_07 = 0.0  → label = 0
MACH-01 : z = (205 - µ_01) / σ_01 = +3.2 → label = 1  ← signal clair

Conséquence attendue : un signal transférable entre machines, une meilleure généralisation en GroupKFold, une variance inter-machine réduite.

02

Mécanisme — Implémentation

Les statistiques µ et σ sont calculées uniquement sur le train du fold courant. Un fallback flotte est appliqué pour les machines sans historique dans le fold.

def normalize_by_machine(df_train_ref, df_to_transform, feature_cols):
    stats     = df_train_ref.groupby("machine_id")[feature_cols].agg(["mean", "std"])
    fleet_mu  = df_train_ref[feature_cols].mean()     # fallback si machine inconnue
    fleet_sig = df_train_ref[feature_cols].std().replace(0, 1)

    result = df_to_transform[feature_cols].copy()
    m_ids  = df_to_transform["machine_id"].reset_index(drop=True)

    for col in feature_cols:
        mu  = m_ids.map(stats[col]["mean"]).fillna(fleet_mu[col])
        sig = m_ids.map(stats[col]["std"]).fillna(fleet_sig[col]).replace(0, 1)
        result[col] = (result[col] - mu) / sig          # z-score par machine

    return result

Le problème GroupKFold — Machine inconnue

Dans un fold GroupKFold, la machine de validation n'a aucune ligne dans le train du fold. Elle ne dispose d'aucune statistique propre. Seul le fallback flotte est disponible.

Diagnostic — Pourquoi ça a échoué

Domain shift train / validation En train : chaque machine est normalisée sur ses propres µ/σ. En validation : la machine inconnue reçoit les µ/σ de la flotte entière. Le modèle évalue des z-scores "flotte" en ayant appris sur des z-scores "machine" — deux référentiels incompatibles. C'est l'inverse de ce qu'on voulait : la normalisation crée le problème qu'elle était censée résoudre.

La bonne approche

La normalisation intra-machine n'est valide que si les statistiques machine sont disponibles au moment de l'inférence. Deux chemins corrects :

Burn-in (production)

La machine collecte N semaines de données avant d'activer les prédictions. Les µ/σ sont calculées progressivement sur l'historique réel.

Pas disponible pendant la validation rétrospective.

Pré-calcul en feature engineering

Les features zscore_machine sont déjà présentes dans gold_machine_hourly_feature, calculées sur l'historique complet de chaque machine.

✓ Disponible immédiatement — c'est la bonne implémentation.

Observation clé Les features zscore_machine avaient été exclues en TP10 pour "éviter le double comptage". C'était une erreur — elles représentent exactement la normalisation correcte, pré-calculée avec le bon historique machine. Il faut les garder, pas les recalculer à l'entraînement.

Limites intrinsèques de la normalisation machine

  • σ instable sur peu de données — moins de 100 observations par machine rendent le z-score bruité
  • Dérive temporelle — si les baselines changent avec l'usure, les stats calculées en début de vie deviennent obsolètes
  • Double normalisation — certaines features sont déjà des z-scores (zscore_machine) ; les re-normaliser n'a pas de sens
06

Règle générale

Principe retenu — TP10

La normalisation intra-machine appliquée à l'entraînement dans un contexte GroupKFold crée un décalage de domaine pour les machines inconnues (val/test). Elle n'est valide que si les statistiques machine sont disponibles au moment de l'inférence — via burn-in en production, ou via les features zscore_machine pré-calculées en feature engineering. Les re-calculer à l'entraînement revient à créer le problème qu'on veut résoudre.
