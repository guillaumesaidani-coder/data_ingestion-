CISIA · Sprint 3 · J3 après-midi · Module 28 — Compose & observabilité

Quatre services, une seule règle : prêt avant de dépendre

Un conteneur qui a démarré n'est pas un conteneur prêt. Ce module fait tenir cette distinction dans un fichier exécutable : l'API n'a le droit de démarrer que si PostgreSQL est healthy, Prometheus que si l'API l'est, Grafana que si Prometheus l'est. Trois TP, une stack qui ne court jamais au démarrage.

3 TP réalisés — 5 tests verts contre la stack réelle jalon 06 · checkpoint M28
TP1 · Écrire le Compose TP2 · Prouver l'ordre de démarrage TP3 · Smoke test & down

Pourquoi

La race condition classique : démarré ≠ prêt

depends_on sans condition ne fait attendre que le lancement du conteneur amont, pas sa disponibilité applicative. Sans plus de précision, Prometheus peut démarrer son premier scrape avant que l'API ait fini de charger son modèle — et Grafana s'ouvrir sur une source de données encore vide.

La règle du module. condition: service_healthy fait attendre le HEALTHCHECK du service amont, pas seulement son démarrage. Ça n'existe que si un HEALTHCHECK est défini — les images officielles Prometheus et Grafana n'en fournissent pas nativement, il faut donc l'écrire soi-même.

TP 1

TP 1Écrire le Compose : 4 services, healthcheck, volumes

Objectif : orchestrer db (postgres:16), api (build local depuis le Dockerfile du jalon 05), prometheus:v3.1.0 et grafana:11.4.0 dans un seul compose.yaml, sans écrire de code applicatif.

  1. db — postgres:16, healthcheck pg_isready -U postgres (interroge le serveur lui-même, pas juste le port TCP), volume nommé pgdata.
  2. api — réutilise le HEALTHCHECK déjà défini dans le Dockerfile (GET /health) : rien à ajouter côté Compose. Reçoit INDUSENSE_DB_URL, construite via le nom de service db (résolution DNS interne à Compose).
  3. prometheus — l'image officielle (busybox minimal) n'a pas de HEALTHCHECK natif ; on en écrit un avec wget --spider contre l'endpoint de readiness de Prometheus lui-même, /-/ready.
  4. grafana — même logique, contre /api/health.
  5. volumes nommés — pgdata, prometheus_data et grafana_data survivent à un down sans -v : pas besoin de réinitialiser la base ni de retélécharger l'historique à chaque redémarrage.
docker compose config -q
# aucune sortie = configuration valide
Piège à éviter. Un service sans HEALTHCHECK ne peut pas être la cible d'un condition: service_healthy — Compose refuserait de démarrer, ou pire, retomberait silencieusement sur un simple service_started selon la version. Le HEALTHCHECK n'est pas cosmétique : c'est la condition elle-même.
Retour formateur. La version publiée ne déclarait que 3 services (api, prometheus, grafana) — le guide attend aussi db (postgres:16) avec son healthcheck, sa dépendance service_healthy côté api, INDUSENSE_DB_URL et le volume pgdata. Ajouté : db ouvre désormais la chaîne de gating, avant même api.

Le décalage entre db (47s), api (40s) et prometheus (17s) est la preuve elle-même : chaque service n'a commencé à exister qu'une fois le précédent devenu sain — api n'a attendu PostgreSQL que quelques secondes (déjà prêt), Prometheus a attendu que l'API charge son modèle.

TP 3Smoke test automatisé, puis down propre

Objectif : remplacer la navigation manuelle (ouvrir 3 onglets, vérifier à l'œil) par un test qui frappe le réseau réel — pas un TestClient in-process — et qui échoue si l'orchestration régresse.

uv run pytest tests/test_smoke_compose.py -q
.....                                                                    [100%]
5 passed in 0.32s
GET /health200 — liveness API
GET /ready200 — modèle chargé
GET /-/ready200 — readiness Prometheus
GET /api/health200 — Grafana database ok
/api/v1/targetshealth="up" pour indusense-api
Piège rencontré, corrigé pour de vrai. Juste après le démarrage, la cible Prometheus affiche encore unknown — le premier scrape (scrape_interval: 15s) n'a pas eu le temps de jouer. Un simple GET une fois passerait à côté : le test retente sur le contenu jusqu'à observer up, pas seulement sur le code HTTP 200.

À l'inverse, quand la stack n'est pas lancée, chaque test se SKIP dès le premier ConnectionError — pas d'échec, pas d'attente de 60s : uv run pytest -q reste vert en local sans Docker.

Repères

Glossaire du module

Liveness
« le processus tourne-t-il ? » — /health, reste toujours ouvert, sinon un orchestrateur redémarre en boucle un service qui n'a juste pas fini de charger.
Readiness
« le service peut-il servir du trafic maintenant ? » — /ready, /-/ready, /api/health : peut échouer sans justifier un redémarrage.
service_healthy
condition depends_on qui attend le HEALTHCHECK du service amont, à distinguer de service_started qui n'attend que le lancement du processus.
Target scrape
dans Prometheus, une source à interroger périodiquement (scrape_configs) ; son état (up/down/unknown) est visible sur /targets.
