CISIA · Sprint 3 · J2 matin · Module 25 — TP3

Une trace qui traverse toute la requête

Un middleware attribue un identifiant unique à chaque requête HTTP — client ou serveur, l'un des deux le fournit toujours, et il revient dans la réponse pour corréler logs et incidents.

Middleware request-id opérationnel /predict-image — extension facultative non implémentée jalon 03 · branche guillaume-saidani

Pourquoi

Retrouver une requête précise dans les logs

Sur un service qui reçoit des centaines d'appels, savoir quelle requête a échoué exige un identifiant qui traverse toute la chaîne — de l'entrée de l'API jusqu'à la ligne de log correspondante. C'est le rôle d'un request-id : soit le client en fournit un (pour corréler avec son propre système), soit l'API en génère un (un uuid4), mais dans tous les cas la réponse le porte dans l'en-tête X-Request-ID.

Ce n'est pas de l'audit logging. Le request-id corrèle les requêtes entre elles ; il ne constitue ni un événement d'audit structuré, ni sa preuve. L'audit logging reste un chantier Planifié v0, traité au module 26.

Le code

Un middleware de 4 lignes

src/indusense/api/main.py, fonction add_request_id — appelée pour chaque requête, avant même l'authentification :

src/indusense/api/main.py
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response

request.headers.get("X-Request-ID", str(uuid.uuid4())) lit l'en-tête envoyé par le client ; s'il est absent, un nouvel identifiant est généré à la volée. Dans les deux cas, il est réinjecté dans les en-têtes de la réponse.

TP 3

TP 3Vérifier X-Request-ID dans la réponse

Deux appels réels à /predict-tabular, l'un sans en-tête côté client, l'autre avec un identifiant fourni :

requête sans X-Request-ID → uuid.uuid4() généré → réponse : X-Request-ID: 52cbc50a-ad1d-4290-9c5e-a0f38a33b0da
requête avec X-Request-ID: demo-trace-42 → valeur client conservée → réponse : X-Request-ID: demo-trace-42

Le client garde la main s'il a déjà son propre système de traçage ; sinon l'API garantit qu'un identifiant existe toujours.

Retour formateur

Vérifié manuellement, mais sans test dédié

Les deux scénarios ci-dessus étaient réels — rejoués à la main contre l'API — mais tests/test_api.py ne contenait aucun test qui les fige en contrat de non-régression. Sur la livraison observée (industrialisation/jalon-03), X-Request-ID reposait donc uniquement sur une vérification manuelle, à côté des tests 401/422/503 eux bien automatisés.

Écart. Le tableau « Obligatoire, fait » ci-dessous listait déjà request-id comme « testé et vert » — c'était vrai du comportement, pas de la preuve automatisée.

Corrigé : deux tests ajoutés à tests/test_api.py, sur /health (aucune clé API requise, isole le middleware du reste) :

Extension facultative

Ce qui n'a pas été fait — et pourquoi ce n'est pas bloquant

Le pas-à-pas propose, « si le groupe avance », de gérer un endpoint /predict-image renvoyant 422 si le fichier reçu n'est pas une image. Cette route n'existe pas dans src/indusense/api/ : elle reste explicitement une extension facultative, non requise par la preuve finale du module 25 (12 tests verts + validateur Model Card), et non implémentée à ce stade.

Obligatoire, fait
/health, /ready, /predict-tabular, request-id — les 4 codes et le middleware sont testés et verts.
Facultatif, non fait
/predict-image — aucun code, aucun test ; à traiter seulement si le temps le permet.
