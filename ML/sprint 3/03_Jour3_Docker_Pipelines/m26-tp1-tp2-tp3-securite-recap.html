CISIA · Sprint 3 · J2 après-midi · Module 26 — Sécurité & menaces

Quatre contrôles prouvés, un cinquième assumé

Une API exposée sur le réseau n'est pas sécurisée parce qu'on l'a « pensée » sécurisée : elle l'est parce que chaque contrôle a un code HTTP observable et un test qui le prouve. Ce module fait exactement cette distinction — priorisé ≠ implémenté.

Pourquoi

Penser comme un attaquant, avec STRIDE

STRIDE découpe les menaces en six familles : Spoofing (usurpation), Tampering (altération), Repudiation (déni d'action), Information disclosure (fuite), Denial of service, Elevation of privilege. L'intérêt n'est pas la liste elle-même, mais l'exercice : pour chaque famille, existe-t-il une preuve — pas une intention — que le risque est couvert ?

La règle du module. Un contrôle « documenté » ou « prévu » n'est pas un contrôle implémenté. Seul un code HTTP observé par un test compte comme preuve. Sur /predict-tabular, quatre familles STRIDE ont une preuve automatisée ; une seule (Repudiation → traçabilité) reste Planifié v0.

TP 1

TP 1Attack tree & contrôles testables

Objectif : transformer STRIDE en deux livrables concrets, sans écrire une ligne de code applicatif.

  1. threat_model.md — pour chaque famille STRIDE, un exemple concret sur /predict-tabular et le contrôle actuel qui y répond (ou son absence assumée). Le pipeline réel est décrit dans l'ordre exécuté : clé API → rate limit → validation Pydantic → chargement du modèle.
  2. security_controls.md — le registre à cinq lignes ci-dessus, avec pour chaque contrôle : statut, preuve actuelle, risque résiduel, action suivante.
  3. La contrainte du registre : exactement quatre lignes Implémenté et une ligne Planifié v0 (audit logging) — jamais l'inverse, jamais un chiffre approché.
Piège à éviter. Écrire « Audit logging : Implémenté » parce que X-Request-ID existe déjà serait faux : ce middleware corrèle des lignes de log entre elles, il ne prouve ni qui a appelé quoi, ni quand, de façon structurée et durable.

TP 2

TP 2Durcir sans casser

Objectif : prouver que les quatre contrôles « Implémenté » tiennent réellement leurs codes, et que /health reste ouvert (c'est la sonde de liveness d'un orchestrateur — la protéger casserait le monitoring).

uv run pytest tests/test_api.py tests/test_security.py -q
...........                                                              [100%]
11 passed, 1 warning in 1.7s
sans clé API401 — require_api_key

Un détail volontaire : le test direct appelle rate_limit 60 fois puis vérifie que le 61ᵉ échoue — c'est une limite exacte, testable de façon déterministe, contrairement à une rafale HTTP réelle qui doit seulement contenir « au moins un 429 ».

TP 3

TP 3Preuve complémentaire — non-divulgation dans les logs

Deux preuves étaient possibles ; celle-ci choisit la non-divulgation : un client envoie une clé API et un machine_id volontairement identifiables comme des marqueurs de test, et le test capture tout ce que loguru écrit pendant la requête.

tests/test_security.py::test_no_secret_or_payload_leak_in_logs
captured = []
logger.add(captured.append, level="TRACE")
client.post("/predict-tabular",
            headers={"X-API-Key": secret_value},
            json={"machine_id": payload_marker, "readings": []})

assert secret_value not in logs_text
assert payload_marker not in logs_text  # PASS
Ce que ce test prouve — et ne prouve pas. Il confirme qu'aucune clé ni aucune donnée du payload ne fuite dans les journaux actuels. Il ne prouve pas qu'un audit logging existe : sans événement structuré (horodatage, request_id, route, code retour) écrit quelque part, la traçabilité en cas d'incident reste absente. D'où le statut Planifié v0, inchangé.

Repères

Glossaire du module

STRIDE
six familles de menaces (usurpation, altération, déni d'action, fuite, déni de service, élévation de privilège) — un canevas pour ne rien oublier, pas une checklist de conformité.
Adversarial
une entrée délibérément truquée pour tromper le modèle ou son pipeline, distincte d'une simple donnée invalide.
Moindre privilège
n'accorder à un client (ou un service) que le strict nécessaire — ici, une clé API unique, tout-ou-rien, sans granularité de rôle.
Planifié v0
un contrôle dont le besoin est identifié et le contrat futur défini, mais sans code ni test aujourd'hui — un statut honnête, pas un contrôle dégradé.
