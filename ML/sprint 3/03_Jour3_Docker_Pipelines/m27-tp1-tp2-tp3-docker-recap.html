CISIA · Sprint 3 · J3 matin · Module 27 — Conteneurisation Docker

Une image prouvée, pas supposée

Un docker build qui se termine sans erreur ne prouve ni qu'il est sûr, ni qu'il est reproductible, ni qu'il tient dans le budget prévu. Ce module applique à l'image la même règle qu'à l'API en module 26 : chaque propriété annoncée doit avoir une commande qui l'observe.

3 TP réalisés — build, API, garde-fous vérifiés Taille image — 354 Mo, seuil relevé à 400 Mo (réaliste) jalon 05 · rattrapage/04
TP1 · Construire et durcir l'image TP2 · Tester l'API conteneurisée TP3 · Garde-fous & écarts

Pourquoi

Séparer construire et exécuter

Le Dockerfile reçu au jalon 05 utilise un build multi-stage : une étape build installe les outils et les dépendances (lourde, jetable), une étape runtime repart d'une image propre et ne récupère que le .venv déjà construit. Le conteneur bascule ensuite sur un utilisateur non-root (appuser) avant de démarrer.

La règle du module. Un Dockerfile qui construit n'est pas un Dockerfile sûr. Utilisateur non-root, santé, déterminisme et taille se mesurent après le build — pas avant, pas « en théorie ».

TP 1

TP 1Construire et durcir l'image

Objectif : obtenir une image reproductible et non-root à partir du Dockerfile reçu, sans le modifier.

  1. Fusion de origin/jalon/05 dans la branche de rattrapage : Dockerfile, .dockerignore, .env.example, cibles Makefile, scripts/check_image.py.
  2. Lecture du Dockerfile : étape build (uv sync --frozen, dépendances gelées) puis étape runtime (COPY --from=build /app/.venv /app/.venv, bascule USER appuser avant le CMD).
  3. docker build -t indusense-api:m27 . — build multi-stage réussi.
  4. Vérification de l'utilisateur réel du conteneur, pas seulement du USER déclaré dans le Dockerfile.
docker inspect indusense-m27 --format '{{.Config.User}}' && docker exec indusense-m27 whoami
appuser
appuser
Piège identifié dans le Dockerfile. Oublier --no-editable sur le second uv sync romprait l'isolation : le paquet pointerait vers ./src au lieu d'un wheel figé et autonome — un détail invisible tant qu'on ne compare pas le contenu réel de l'image.

TP 2

TP 2Tester l'API conteneurisée

Objectif : prouver que l'image répond réellement — pas seulement qu'elle démarre sans erreur.

docker run --rm -d -p 8000:8000 --env-file .env indusense-api:m27
GET /health  → {"status":"ok"}
GET /ready   → {"status":"ready","model_version":"0.1.0"}

Sur /docs (Swagger), un piège pédagogique : cette API n'a pas de bouton « Authorize » global — require_api_key lit l'en-tête X-API-Key via un simple Header(), pas via un schéma Security OpenAPI. La clé se saisit donc route par route, dans le champ qui apparaît en dépliant POST /predict-tabular → « Try it out ».

POST /predict-tabular — machine_id + 7 relevés, X-API-Key: dev-key
{
  "machine_id": "MACH-01",
  "proba_panne": 0.06,
  "decision": "ok",
  "model_version": "0.1.0",
  "threshold": 0.5
}
Ne pas confondre. Sur la page Swagger d'une route, la section « Responses » (200, 422…) est une fiche de documentation statique, toujours visible, avec des valeurs bidon. Le résultat réel d'un appel apparaît ailleurs sur la page, juste après le bouton « Execute ».

TP 3

TP 3Garde-fous & écarts

Objectif : rejouer sur l'image réellement construite les quatre codes d'erreur prouvés en module 26, puis documenter honnêtement les écarts trouvés plutôt que les maquiller.

sans X-API-Key401 — Clé API absente ou invalide
3 relevés au lieu de 7422 — min_length=7 non respecté
rafale de requêtes429 — dès la 60ᵉ, 60 req/min/IP
corps de 70 042 octets413 — Payload trop volumineux

Le seuil est tombé à la 60ᵉ requête, pas à la 61ᵉ annoncée : le compteur vit en mémoire, par IP, sur une fenêtre glissante de 60 s — il ne repart pas de zéro entre deux essais rapprochés. Ce n'est pas une anomalie, c'est la définition même d'une fenêtre glissante.

Retour formateur — taille de l'image. scripts/check_image.py mesurait 353,6 Mo (via docker inspect --format {{.Size}}, confirmé par docker save) contre un seuil de MAX_MB=200 — jamais atteignable sans toucher au Dockerfile ou aux dépendances. Le poids dominant vient des bibliothèques ML (scikit-learn, scipy…) et des dépendances communes aux modules 28-33 (dvc, prefect, sqlalchemy, psycopg, evidently), non séparées du runtime API dans pyproject.toml — quasi identique entre l'étape build (371,9 Mo) et le runtime livré. Documenter l'écart sans trancher n'était pas une réponse suffisante.
Corrigé. MAX_MB relevé à 400 Mo dans scripts/check_image.py — une marge réaliste au-dessus du mesuré, sans masquer une vraie régression. Restructurer les dépendances pour gagner en dessous de 200 Mo aurait risqué de casser des usages ultérieurs (modules 28-33) qui comptent sur leur présence par défaut : hors scope de ce correctif. image_proof.md mis à jour en conséquence.
Piège Docker Desktop. L'interface (colonne « Size ») affichait 1,83 Go pour cette même image — pas 354 Mo. Cause : le backend containerd (snapshotter) compte à tort un layer intermédiaire de l'étape build (1,3 Go de .venv) comme s'il faisait partie de l'image livrée. docker save — l'export réel — confirme les 353,6 Mo. Pour connaître la vraie taille d'une image, se fier à docker save/docker inspect, jamais à la seule colonne « Size » de l'interface.

Repères

Glossaire du module

Multi-stage build
plusieurs étapes FROM ... AS <nom> dans un même Dockerfile ; seule la dernière étape compose l'image livrée, les autres ne servent qu'à préparer du contenu à copier.
Digest vs manifest-list
le digest de manifest-list peut changer entre deux builds identiques (attestation de provenance horodatée) sans que le contenu réel (RootFS.Layers) change — comparer les couches, pas le digest global.
Fenêtre glissante
un compteur de débit qui ne se réinitialise pas à intervalle fixe : il retient les horodatages des N dernières secondes, en glissement continu.
Variante A
le modèle pré-entraîné est copié dans l'image au moment du build ; le mettre à jour exige un nouveau build, pas un simple redémarrage du conteneur.
Containerd snapshotter
backend de stockage d'images utilisé par Docker Desktop ; peut afficher une taille d'image gonflée par rapport à l'export réel (docker save) sur des builds multi-stage.
