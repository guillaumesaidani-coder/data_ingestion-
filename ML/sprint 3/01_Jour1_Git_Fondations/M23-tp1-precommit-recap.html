Pre-commit & secrets

Installer des gardiens qui tournent avant chaque commit — pour attraper le style, le formatage et les secrets avant qu'ils n'entrent dans l'historique Git.

TP validé — 3 hooks verts jalon 02 · branche guillaume-saidani

Pourquoi

Un gardien avant le commit, pas après

La CI (.github/workflows/ci.yml) détecte un problème après le push — trop tard, le mauvais code est déjà dans l'historique partagé. Pre-commit installe les mêmes contrôles en local, déclenchés automatiquement à chaque git commit : le problème est bloqué avant même de quitter ta machine.

Un « gardien », c'est quoi ? Un hook pre-commit : un contrôle automatique qui s'exécute à chaque tentative de commit, avant que le code n'entre dans l'historique Git. S'il échoue, le commit est refusé — le problème reste sur ta machine, jamais partagé.

.pre-commit-config.yaml définit trois gardiens :

ruff --fix
lint et corrige automatiquement ce qui peut l'être — contrairement à la CI qui ne fait que signaler
black
reformate le code directement — pas de --check ici, ce hook corrige plutôt que de constater
gitleaks
scanne le contenu à committer et bloque le commit si un secret (clé API, token…) est détecté

Étape 1

Installer les hooks

TP 1Deux points d'accroche : pre-commit et pre-push

pre-commit se déclenche à chaque commit local ; pre-push se déclenche juste avant l'envoi vers origin — une deuxième chance d'attraper un oubli.

uv run pre-commit install --hook-type pre-commit --hook-type pre-push
pre-commit installed at .git\hooks\pre-commit
pre-commit installed at .git\hooks\pre-push

Étape 4

Démo secret bloqué — réversible

Un fichier avec une clé AWS d'exemple, publique et invalide (documentation officielle AWS, jamais une vraie clé même révoquée) est ajouté à l'index, puis scanné par gitleaks seul — sans jamais tenter un vrai commit :

uv run pre-commit run gitleaks --files fuite_demo.txt
Detect hardcoded secrets.................................................Failed
- hook id: gitleaks
- exit code: 1

Finding:     AWS_ACCESS_KEY_ID=REDACTED
RuleID:      aws-access-token
Entropy:     3.684184
File:        fuite_demo.txt
Line:        2

leaks found: 1

Résultat exact attendu, obtenu à l'identique : RuleID: aws-access-token, leaks found: 1. Un vrai git commit aurait été bloqué net.

Pourquoi le secret n'atteint jamais un commit réel. Le hook pre-commit s'exécute avant que Git ne crée l'objet commit dans .git. gitleaks a rendu un code de sortie non nul (exit code: 1) — Git interprète ça comme un refus et interrompt le commit : aucun objet n'est écrit dans l'historique, le fichier reste seulement dans l'index (staging area), à l'état de simple ajout réversible. Ici, ni même un vrai git commit n'a été tenté : le TP invoque directement pre-commit run gitleaks sur le fichier indexé, pour tester le hook sans aucun risque d'écrire quoi que ce soit dans l'historique.
Détecté
gitleaks refuse le fichier — le secret n'entre jamais dans un commit
Nettoyage
git restore --staged -- fuite_demo.txt puis suppression du fichier
Vérifié
git status --short ne montre plus rien — dépôt propre, rien committé

Repères

Local vs CI — même règles, deux moments

Hook
Un script déclenché automatiquement par Git à un moment précis (pre-commit, pre-push…).
Local corrige, CI constate
En local, ruff --fix et black (sans --check) réparent. En CI, black --check et ruff check ne font que signaler — la CI ne doit jamais modifier le code à ta place.
Pourquoi révoquer, pas juste supprimer
Un secret committé reste dans l'historique Git même après suppression du fichier — exploitable jusqu'à révocation côté fournisseur.
