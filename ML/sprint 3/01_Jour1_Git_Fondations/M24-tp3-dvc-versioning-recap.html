Versionner données et modèle avec DVC

Un CSV et un .joblib ne rentrent pas dans git comme du code — DVC leur donne un pointeur léger versionné, pendant que le vrai fichier part vers un remote.

TP validé — data + modèle migrés vers DVC jalon 02 · branche guillaume-saidani

Pourquoi

Git versionne du texte, pas des gigaoctets

Un gold_dataset.csv ou un rf.joblib committé directement dans git grossit l'historique à chaque ré-entraînement, sans que git diff n'apporte rien sur un contenu binaire. DVC déplace le poids du fichier vers un remote (ici un dossier local, ../../dvc-store), et ne laisse dans git qu'un petit pointeur texte : un hash MD5, une taille, un chemin.

gold_dataset.csv (281 Ko) dvc add → gold_dataset.csv.dvc → suivi par git
Séparation des rôles. Git suit le pointeur (petit, diffable, versionné pour toujours). DVC déplace le fichier réel vers le remote et le restaure via dvc checkout — le poids sort de l'historique git.

Le pointeur

Ce que contient un fichier .dvc

Deux pointeurs ont été créés par dvc add data/gold/gold_dataset.csv artifacts/models/rf.joblib :

Un .gitignore a été généré automatiquement dans chaque dossier (/gold_dataset.csv, /rf.joblib) : le fichier réel reste sur disque pour travailler localement, mais git ne le voit plus — seul le .dvc à côté est suivi.

Migration, pas ajout à neuf. Les deux fichiers étaient déjà suivis par git (héritage du socle Sprint 2/3). dvc add refuse un fichier encore indexé par git : il a fallu d'abord git rm -r --cached chacun avant de le confier à DVC — c'est ce que trace le diff (suppression de rf.joblib et gold_dataset.csv côté git, apparition des .dvc côté non-suivi).

Traçabilité

Une empreinte = une version des données

Le script scripts/demo_versioning.py calcule le MD5 du gold (gold_md5) et l'inscrit dans artifacts/models/model_metadata.json, dans le nom du run MLflow, et dans le tag git suggéré en fin de script. Si le CSV change d'un seul octet, cette empreinte change — on sait immédiatement quelle version de données a produit quel modèle.

MLflow

Params, métriques et registre, en parallèle de DVC

MLflow trace ce que DVC ne trace pas : les réglages et les résultats d'un entraînement, pas le poids d'un fichier. Le backend est SQLite (mlflow.db) plutôt qu'un simple dossier mlruns/, parce que le Model Registry — qui nomme et numérote les versions de modèle (indusense-rf v1, v2…) — en a besoin.

uv run python scripts/demo_versioning.py
== 1. Entrainement ==
   split=temporel/machine | train=1516 test=380 | PR-AUC=0.1036 ROC-AUC=0.2475 seuil=0.975 recall=0.0
== 2. MLflow (params + metriques + modele + registre) ==
   modele enregistre au registre : 'indusense-rf'
== 3. DVC (versionner data + modele) ==
   -> 2 pointeurs crees : data/gold/gold_dataset.csv.dvc + artifacts/models/rf.joblib.dvc

metrics.json et params.yaml sont écrits en clair et versionnés par git (pas par DVC — ils sont petits et lisibles) : c'est ce que lisent dvc metrics show et dvc params diff pour comparer deux commits sans rouvrir MLflow.

Signal à ne pas ignorer. Le seuil 0.975 a été calibré pour maximiser le F1 sur le train — et donne recall=0 et precision=0 sur le test : le modèle ne détecte plus aucune panne. Un seuil optimisé sur le train qui s'effondre sur le test est le même symptôme que la fuite de données du module 23 : ce qui marche à l'entraînement ne garantit rien en conditions réelles. La démo verse ce résultat imparfait dans MLflow tel quel — c'est la traçabilité qui est évaluée ici, pas la performance du modèle.

Figer la version

Ce que le script propose de lancer ensuite

Le script n'exécute pas git commit à la place de l'apprenant : il affiche les commandes à copier-coller pour figer cette version de données+modèle.

  1. 1git add data/gold/gold_dataset.csv.dvc artifacts/models/rf.joblib.dvc .gitignore metrics.json params.yaml — seuls les pointeurs et les fichiers texte entrent dans git.
  2. 2git commit -m "data+model 637be8d38250 | PR-AUC 0.1036" — le message embarque directement l'empreinte et la métrique clé.
  3. 3git tag data-637be8d38250 — une étiquette lisible pour revenir exactement à cette version de données+modèle plus tard.
  4. 4dvc push puis git switch --detach data-637be8d38250 && dvc checkout — envoie le fichier réel vers le remote, puis prouve qu'on peut le restaurer depuis n'importe quel commit tagué.

Repères

Vocabulaire DVC / MLflow

Pointeur .dvc
Fichier texte versionné par git à la place du gros fichier — contient hash, taille et chemin.
Remote DVC
Où part le contenu réel des fichiers suivis — ici un dossier local ../../dvc-store, configuré dans .dvc/config.
dvc checkout
Restaure les fichiers réels correspondant aux pointeurs du commit courant.
Model Registry
Côté MLflow : nomme et numérote les versions successives d'un modèle enregistré (indusense-rf).
gold_md5
Empreinte du jeu de données au moment de l'entraînement — relie un modèle à sa version exacte de données.
