Pourquoi

Un script racine ne rentre pas dans une image Docker

Le Dockerfile ne copie que src/ dans l'image finale (COPY src ./src) — c'est la logique même du build multi-stage du module 27 : rien de superflu dans l'image livrée. Le fichier flows/pipeline.py du module 29, à la racine du dépôt, n'existe donc pas dans le conteneur. Pour lancer le pipeline via docker compose run ... api python -m indusense.flows.predict_flow comme le demande le guide, la logique doit vivre dans le paquet indusense, au même titre que l'API ou les loaders.

La règle du module. Le paquet est la source de vérité ; le script racine n'est plus qu'une façade. flows/pipeline.py ne contient désormais que trois lignes utiles : un import depuis indusense.flows.predict_flow et un appel à main(). Zéro logique dupliquée entre les deux points d'entrée.

TP 1Déplacer le flow dans le paquet, garder une seule logique

Objectif : que uv run python flows/pipeline.py (la commande de preuve du jalon) et python -m indusense.flows.predict_flow (la commande du conteneur) lancent exactement le même code.

src/indusense/flows/predict_flow.py

Les 5 @task, le @flow indusense_pipeline, la fonction de nom de run. Installé dans le .venv par uv sync comme n'importe quel autre module du paquet — donc présent dans l'image Docker.

flows/pipeline.py

from indusense.flows.predict_flow import indusense_pipeline, main puis if __name__ == "__main__": main(). Rien d'autre — une façade, pas une deuxième implémentation.

Piège évité. Dupliquer le flow (une version racine « pour le jalon », une version paquet « pour Docker ») aurait fonctionné à court terme, mais aurait créé deux vérités à maintenir en parallèle — la première divergence serait passée inaperçue jusqu'au jour où un correctif appliqué d'un seul côté casse la reproductibilité entre local et conteneur.

TP 2

TP 2Stocker via SQLAlchemy, sans brancher SQLite vs Postgres

Objectif : remplacer le sqlite3 brut du module 29 par un accès qui fonctionne aussi contre PostgreSQL — sans if backend == "postgres": ... else: ... dans le code.

  1. Une seule URL — INDUSENSE_DB_URL, lue par create_engine(db_url). En local : sqlite:///artifacts/predictions.db. Sous Compose : postgresql+psycopg://postgres:...@db:5432/postgres, injectée par compose.yaml pour le service api.
  2. Un seul SQL — INSERT INTO predictions (...) VALUES (...) ON CONFLICT (machine, observed_at) DO UPDATE SET ... = excluded..... Ce n'est pas une coïncidence : Postgres et SQLite (≥ 3.24) partagent la même syntaxe d'upsert standard, ce qui rend le code portable sans dialecte à gérer.
  3. Types portables — TEXT et DOUBLE PRECISION : valides nativement en Postgres, et acceptés par le typage dynamique de SQLite (affinité de type) sans erreur.
src/indusense/flows/predict_flow.py
_UPSERT_SQL = """
INSERT INTO predictions (machine, observed_at, score, decision, model_version, scored_at)
VALUES (:machine, :observed_at, :score, :decision, :model_version, :scored_at)
ON CONFLICT (machine, observed_at) DO UPDATE SET
    score = excluded.score,
    decision = excluded.decision,
    model_version = excluded.model_version,
    scored_at = excluded.scored_at
"""

--no-depsne redémarre pas prometheus/grafana pour un simple run
--volume ...:/app/data/run:rodonnées montées, jamais copiées dans l'image
modèle Variante Adéjà dans l'image (module 27) → reprise immédiate
Piège rencontré, corrigé pour de vrai. Sous Git Bash sur Windows, tout argument ressemblant à un chemin absolu Unix (-e INDUSENSE_DATA_DIR=/app/data/run) est réécrit en chemin Windows par la conversion automatique MSYS avant d'atteindre Docker — le conteneur recevait littéralement C:/Program Files/Git/app/data/run et échouait avec FileNotFoundError. Corrigé en exportant MSYS_NO_PATHCONV=1 autour de la commande : rien à changer côté pipeline, c'est une particularité du shell, pas du code.

Repères

Glossaire du module

Engine SQLAlchemy
objet créé par create_engine(url) qui gère la connexion et le pool ; change de backend en changeant seulement l'URL, pas le code SQL.
Upsert portable
INSERT ... ON CONFLICT ... DO UPDATE : syntaxe supportée nativement par SQLite (≥3.24) et PostgreSQL — un seul jeu de requêtes pour les deux backends.
docker compose run --no-deps
exécute une commande ponctuelle dans un nouveau conteneur du service donné, sans démarrer les services dont il dépend (utile si db tourne déjà).
Volume en lecture seule
:ro sur un montage --volume : le conteneur peut lire les données hôte mais jamais les modifier — la source reste intacte.
MSYS_NO_PATHCONV
variable qui désactive la conversion automatique des chemins Unix en chemins Windows par Git Bash — nécessaire dès qu'on passe un chemin destiné à l'intérieur d'un conteneur.
