Dérive PayGuard

Trois semaines de production d'un modèle anti-fraude, auditées avec deux instruments codés à la main (PSI, KS), puis confrontées aux vrais labels. Ce que ça donne, étape par étape.

Modèle
HistGradientBoosting, seuil gelé à 0,03
Coût d'une erreur
fraude ratée ≈ 50 € · vérification inutile ≈ 2 €
Fenêtre auditée
3 semaines de prod × 3 000 transactions

Étapes 0–1Le dispositif surveillé

PayGuard note chaque transaction carte d'un site e-commerce. Au-dessus du seuil gelé (0,03 — un score de probabilité, pas une somme en euros), la transaction part en vérification manuelle. Cinq features alimentent le modèle et sont surveillées chaque semaine :

D'où vient 0,03 :

  coût = 50 € × FN + 2 € × FP # sur la validation

Étape 2Deux instruments, codés à la main

scripts/drift_lab.py contenait trois trous à combler : psi(), ks_pvalue() et drift_table(). Le piège tenait en une ligne — que fait np.histogram d'une valeur de production hors de la plage de référence ? Il l'ignore. La correction : ouvrir les bords extrêmes à l'infini.

# psi(ref, cur, bins=10) — le piège des valeurs hors plage
edges = np.histogram_bin_edges(ref, bins=bins)
edges[0] = -np.inf
edges[-1] = np.inf

p_ref = np.histogram(ref, edges)[0] / len(ref) + 1e-6
p_cur = np.histogram(cur, edges)[0] / len(cur) + 1e-6
return np.sum((p_cur - p_ref) * np.log(p_cur / p_ref))

drift_table() boucle les 5 features, appelle les deux fonctions, trie par PSI décroissant. Verdict : 12 tests verts (uv run python -m pytest), 0 échec.

Étapes 3–5Trois semaines, sans les labels

Le label fraude n'existe pas au moment de la transaction — personne ne sait encore si c'est frauduleux, ni le modèle ni l'équipe risque. Il naît au bout d'une chaîne bien réelle :

JTransaction scorée et décidée tout de suite, seuil gelé — sans savoir si la décision est bonne
→
RelevéLe client ne découvre l'opération qu'en consultant son relevé bancaire
→
ContestationIl signale l'opération — fenêtre de plusieurs semaines à plusieurs mois selon les réseaux
→
InstructionLa banque/le marchand vérifie et tranche — c'est seulement là que le label existe

Impossible de mettre les décisions en pause en attendant : sur les trois premières semaines, seule la distribution des entrées est observable — c'est le covariate monitoring. Le même problème existe pour le crédit (défaut connu des mois après) ou l'attribution publicitaire (conversion connue en différé).

Ce que ça révèleLa limite structurelle

PSI et KS ne mesurent qu'une chose : P(X), la distribution des entrées. Ils ne regardent jamais la relation entre ces entrées et le label — P(Y|X). Les deux peuvent dériver indépendamment l'une de l'autre :

Covariate drift semaine 2
Ce qui bouge
P(X) — les habitudes d'achat
PSI le voit ?
Oui — jusqu'à 0,47
Le modèle
continue de fonctionner (rappel 0,92)
Concept drift semaine 3
Ce qui bouge
P(Y|X) — le sens même de la fraude
PSI le voit ?
Non — max 0,006, RAS partout
Le modèle
s'effondre (rappel 0,072, ROC-AUC 0,278)

Ce n'est pas un bug à corriger. Aucune version plus fine de PSI ou de KS ne comblera cet angle mort : par construction, ces tests ne regardent que les entrées. Un modèle peut s'effondrer sans qu'aucune alerte amont ne se déclenche.

Conséquence actée dans la drift spec : le monitoring des entrées ne peut jamais garantir que le modèle fonctionne — seul le KPI métier (le rappel), disponible une fois les labels arrivés, peut le confirmer. La surveillance amont détecte vite ce qu'elle peut voir ; elle ne remplace pas l'évaluation avec labels, elle la complète.

Étape 7La drift spec

reports/drift_spec_payguard.md fige les décisions pour que la surveillance cesse d'être arbitraire :

Référence
20 000 transactions, gelée avec le modèle — remplacée uniquement lors d'un réentraînement officiel
Fenêtre & fréquence
1 semaine glissante, calcul hebdomadaire, ≥ 1 000 transactions minimum
Seuil d'alerte
PSI > 0,25 sur ≥ 2 features · rappel < 0,70
KPI métier
rappel fraude au seuil gelé, dès que les labels tombent
Réaction
PSI seul → investiguer, rapprocher d'un événement métier · rappel sous plancher → réentraînement, jamais un simple ajustement de seuil
Limite connue
structurellement aveugle au concept drift — la semaine 3 en est la preuve

PérimètreEnvironnement & ce qui n'existe pas

Un point de méthode avant de refermer : PayGuard est un scénario métier, pas un service qui tourne quelque part. Il n'y a ni serveur de prod, ni API, ni déploiement dans ce dépôt — seulement des scripts qui simulent le cycle (entraînement, scoring batch sur des CSV, calcul de dérive, évaluation). Le TP le dit explicitement (étape 9) : le lien vers un vrai déploiement (Docker, Prefect, dashboard) est prévu pour les modules 33-34, sur le repo InduSense.
