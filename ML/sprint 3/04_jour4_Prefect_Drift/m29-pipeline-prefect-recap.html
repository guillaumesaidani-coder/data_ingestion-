CISIA · Sprint 3 · J4 matin · Module 29 — Orchestration Prefect & idempotence

Rejouer le pipeline ne doit jamais l'abîmer

Un script qu'on relance à la main pose toujours la même question anxiogène : « si je le relance, est-ce que ça va dupliquer quelque chose ? ». Ce module transforme le script d'entraînement/prédiction en flow Prefect — des étapes nommées, une reprise qui évite de refaire un travail déjà fait, et un stockage qui remplace au lieu d'ajouter.

Flow lancé 2 fois de suite — 4 lignes en base, toujours 4 jalon 07 · checkpoint M29
TP1 · Découper en tasks/flow TP2 · Cache & reprise TP3 · Prouver l'idempotence Glossaire

Pourquoi

Un script n'a pas de mémoire ; un flow, si

uv run indusense train puis predict à la main ne sait rien de ses propres exécutions passées. Chaque relance réentraîne le modèle même si rien n'a changé, et chaque prédiction écrite quelque part s'ajoute à la précédente sans vérifier si elle existe déjà. Sur un pipeline qui tourne en boucle (cron, retry après panne réseau, reprise après un plantage), ça veut dire : du calcul gâché, et une base qui grossit à l'infini avec des doublons.

La règle du module. Un flow Prefect découpe le travail en tasks : chacune peut être mise en cache (rejouée depuis un résultat déjà connu, sans recalcul) ou reprise (sautée si son effet existe déjà). La dernière étape — écrire les résultats — doit en plus être idempotente : rejouée deux fois sur les mêmes données, elle produit le même état, jamais un état doublé.

TP 2

TP 2Cache sur l'ingestion, reprise sur l'entraînement

Objectif : ne pas relire ni rejoindre les trois fichiers source, ni réentraîner un modèle, si rien de pertinent n'a changé depuis la dernière exécution — même dans un nouveau process (la preuve doit survivre à la fermeture du terminal).

  1. Clé de cache — _sources_cache_key() calcule une empreinte SHA-256 à partir de la date de modification et de la taille des 3 fichiers source, plus window_hours. Tant que cette empreinte ne change pas, Prefect renvoie le résultat déjà connu au lieu de relancer build_gold_dataset.
  2. Reprise sur le modèle — ensure_model commence par vérifier model_path.exists() : si un modèle est déjà là et que retrain=False, il est réutilisé tel quel, sans passer par RandomForestClassifier.fit().
2ᵉ lancement, process frais, mêmes fichiers source
Task run 'build-gold-dataset-422' - Finished in state Cached(type=COMPLETED)
Task run 'ensure-model-22e'       - Reprise : modele existant reutilise -> artifacts\models\rf.joblib
Task run 'ensure-model-22e'       - Finished in state Completed()

Ces deux lignes sont la preuve directe : Cached signifie que l'ingestion n'a pas été rejouée du tout, et le message « Reprise » confirme que l'entraînement a été sauté volontairement, pas oublié.

TP 3

TP 3Prouver qu'un second passage ne duplique rien

Objectif : la dernière task, store-predictions, écrit dans une base SQLite. Rejouer le flow deux fois sur les mêmes données doit laisser le même nombre de lignes — pas le double.

Mécanisme : chaque ligne est identifiée par la clé composite (machine, observed_at). L'écriture utilise INSERT ... ON CONFLICT(machine, observed_at) DO UPDATE : si la clé existe déjà, la ligne est mise à jour (nouveau score, nouvel horodatage) au lieu d'être ajoutée.

uv run --frozen python scripts/demo_prefect_idempotence.py
1er passage : rows_scored=4 rows_in_db=4
2e  passage : rows_scored=4 rows_in_db=4
OK idempotence : 4 lignes stables apres 2 passages (...\indusense-preuve-ck2omwul\predictions.db)
base neuve à chaque lancement du scriptjamais une base déjà remplie, sinon la preuve serait truquée
comptage indépendantSELECT COUNT(*), pas seulement la valeur renvoyée par le flow
échec explicitele script sort en erreur (code 1) si les comptes divergent
Piège rencontré, corrigé pour de vrai. Le premier essai ouvrait la connexion SQLite avec with sqlite3.connect(...) as conn: — ce context manager ne fait que committer/annuler la transaction, il ne ferme pas la connexion. Sous Windows, le fichier restait verrouillé et le nettoyage du dossier temporaire échouait avec PermissionError. Correction : with closing(sqlite3.connect(...)) as conn:, qui garantit la fermeture réelle.

Repères

Glossaire du module

Task
une fonction Python décorée @task : une unité de travail que Prefect peut suivre, mettre en cache et relancer indépendamment des autres.
Flow
la fonction @flow qui orchestre l'appel aux tasks dans l'ordre ; chaque appel du flow est un flow run, identifiable par son nom.
Cache key
une empreinte calculée à partir des entrées d'une task ; une empreinte identique permet à Prefect de renvoyer le résultat déjà connu sans réexécuter la task.
Reprise
sauter une étape dont l'effet (fichier, modèle) existe déjà sur disque, vérifié explicitement dans le code de la task — complémentaire du cache Prefect.
Idempotence
propriété d'une opération qu'on peut répéter sans changer le résultat au-delà du premier appel — ici, un état stable en base plutôt qu'une croissance à chaque relance.
Upsert
INSERT ... ON CONFLICT ... DO UPDATE : insère si la clé n'existe pas, met à jour sinon — le mécanisme SQL qui rend le stockage idempotent.
