Hors Compose : comment tournent-ils en formation ?

Aucun des trois n'est vraiment « déployé » — ce sont des exécutions manuelles, locales.

drift exporter foreground

uv run python scripts/export_drift_metrics.py

Lancé à la main dans un terminal, gardé ouvert (« terminal 1 » du TP). Pas de démon, pas de service système — rien ne redémarre si le terminal se ferme.

Prefect ephemeral

uv run --frozen python flows/pipeline.py # ou, en conteneur jetable : docker compose run --rm --no-deps \ api python -m indusense.flows.predict_flow

Deux façons, aucune n'est un vrai déploiement Prefect (ni serveur, ni agent, ni UI). Le second cas utilise l'image api du compose mais pas comme service persistant — juste un run ponctuel. Et PREFECT_PROFILE=ephemeral est explicitement fixé (GUIDE_MULTIPLATEFORME_APPRENANT.md:398) : aucun serveur Prefect, état local jetable.

MLflow pas de serveur

uv run python scripts/demo_versioning.py

Encore plus minimal : pas de serveur du tout. mlflow.db (SQLite) et mlruns/ à la racine sont juste le backend de tracking local par défaut, créés par ce script — le seul du repo à utiliser réellement MLflow.

Bref : cohérent avec un repo de formation — ce sont des exécutions pédagogiques ponctuelles, pas des services en production.

Bonnes pratiques — faut-il les conteneuriser ?

ComposantEn productionPourquoi
drift exporter oui, à conteneuriser un service compose de plus, scrapé par son nom de service interne — pas par host.docker.internal, qui est un hack de dev/pédagogie. Le laisser sur l'hôte casse la reproductibilité et le déploiement.
Prefect selon l'usage en local/dev, un agent Prefect peut tourner en conteneur dans le compose ; en prod on utilise plutôt Prefect Cloud ou un déploiement séparé (k8s, service managé) — pas forcément le même compose applicatif.
MLflow optionnel généralement un service à part, souvent mutualisé entre plusieurs projets avec son propre stockage d'artefacts. L'ajouter à ce compose serait acceptable, mais pas obligatoire.

Bonnes pratiques détaillées, par composant

drift exporter

  • Conteneurisé, service interne sans port publié, scrapé par nom de service — pas de port exposé à l'hôte.
  • restart: unless-stopped + healthcheck, comme les autres services.
  • Modèle pull (Gauge + /metrics) adapté à un process long-lived ; pour un batch court, préférer un Pushgateway plutôt qu'un serveur HTTP à maintenir vivant.
  • Chemins et seuils via variables d'environnement, jamais en dur.

Prefect

  • Sortir du profil ephemeral : un vrai serveur (auto-hébergé ou Prefect Cloud) avec backend Postgres, pas SQLite local.
  • Déploiements déclarés (prefect deploy / prefect.yaml), versionnés, avec schedule ou trigger explicite — pas un script lancé à la main.
  • Un ou plusieurs workers dans un work pool dédié, conteneurisés, scalables indépendamment de l'API.
  • Secrets (DB, clés d'API) via Prefect Blocks ou un vault, jamais en variables inline.

MLflow

  • Serveur de tracking centralisé (mlflow server) mutualisé entre projets — pas un mlruns/ local par repo.
  • Metadata sur une vraie base (Postgres), artefacts sur un stockage objet (S3/GCS/Azure Blob), jamais le disque local du conteneur.
  • Derrière une auth / reverse proxy.
  • Gouvernance des transitions du Model Registry (staging → production).

Transverses, aux trois

  • Infra as code (compose ou k8s versionné + CI/CD qui build et pousse les images) — pas de docker compose up --build manuel sur un poste.
  • Limites CPU/mémoire par service, logs sur stdout, secrets hors du dépôt (vault / secret manager).
  • Sauvegardes pour tout ce qui est stateful (bases, stockage d'artefacts, volumes Prometheus/Grafana).

Ce qu'apporterait Kubernetes, en prod réelle

Scaling & auto-scaling — répliquer api selon la charge (HPA), impossible nativement en Compose.
Self-healing — un pod qui plante est relancé automatiquement, un nœud qui tombe fait migrer les pods ailleurs.
Rolling updates / rollback — déploiement progressif sans coupure, retour arrière en une commande.
Bin packing multi-machines — Compose reste sur un seul hôte ; k8s répartit la charge sur un cluster.
Service discovery + load balancing natifs — un Service équilibre entre plusieurs replicas, pas une instance unique par service.
Secrets/config déclaratifs — Secret / ConfigMap avec RBAC et rotation, plutôt qu'un .env en clair.
Ingress/TLS centralisé — un contrôleur d'entrée gère certificats et routage pour tous les services.
Écosystème d'opérateurs — Prefect (workers en Deployment scalable), kube-prometheus-stack, opérateur Postgres avec failover, etc.
Le coût en face : complexité opérationnelle largement supérieure — etcd, control plane, réseau CNI, RBAC, manifests ou Helm. Se justifie à partir de plusieurs nœuds, d'une charge variable, ou de plusieurs environnements (dev/staging/prod) à répliquer proprement.
Pour InduSense aujourd'hui : stack mono-nœud, Compose reste largement suffisant. Kubernetes deviendrait pertinent si le projet passait en multi-instances avec disponibilité exigée.
Hors Compose : l'exporteur de drift (module 31-32, terminal séparé), les flows Prefect et le tracking MLflow tournent en dehors de cette stack — voir docs/TP_drift.md. C'est un choix pédagogique par module, pas une recommandation de production : voir les sections ci-dessus.
