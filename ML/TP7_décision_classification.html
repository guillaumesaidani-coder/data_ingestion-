Compétence 1

Choisir et justifier 3 algorithmes baseline

En classification tabulaire, on ne choisit pas arbitrairement — chaque algorithme apporte une hypothèse différente sur la structure des données. On compare du plus simple au plus expressif.

Baseline linéaire
Régression Logistique
LogisticRegression

Modèle linéaire qui estime la probabilité P(panne) via une combinaison pondérée des features. Suppose que la frontière de décision est linéaire dans l'espace des features.

Pourquoi le choisir Référence minimale incontournable. Si LR performe bien, la relation feature→cible est suffisamment linéaire — et le modèle reste interprétable directement via ses coefficients. Si LR échoue, cela justifie les modèles non-linéaires suivants.
PR-AUC val = 0.357 Relation non-linéaire Interprétable
Ensemble — bagging
Random Forest
RandomForestClassifier

Agrège des centaines d'arbres de décision entraînés sur des sous-échantillons aléatoires. Chaque arbre vote, la majorité l'emporte. Robuste aux valeurs aberrantes et aux features redondantes.

Pourquoi le choisir Capture les non-linéarités et interactions entre features sans paramétrage fin. Référence solide pour données tabulaires hétérogènes — souvent plus difficile à battre qu'on ne le pense.
PR-AUC val = 0.768 Robuste overfitting Peu sensible aux déséquilibres

XGBoost
XGBClassifier

Construit des arbres séquentiellement — chaque arbre corrige les erreurs du précédent. Le paramètre scale_pos_weight compense nativement le déséquilibre de classes (~28×).

Pourquoi le choisir État de l'art sur données tabulaires. Gère le déséquilibre de classes, les valeurs manquantes, et offre un espace d'optimisation étendu (L1/L2, max_depth, early stopping).

Compétence 2

Calculer et interpréter les métriques

Valeurs calculées sur les résultats XGBoost TP7 : TP = 639, FP = 366, FN = 88, TN = 18 851. Total = 19 944 observations.

Accuracy
(TP + TN) / N
= (639 + 18851) / 19944
97.7 %

Trompeuse ici : prédire «OK» en permanence donnerait ~96.4 %. L'accuracy ignore le déséquilibre.

Precision
TP / (TP + FP)
= 639 / (639 + 366)
63.6 %

Sur 1 005 alertes émises, 639 étaient de vraies pannes. 36 % sont des fausses alarmes.

Recall
TP / (TP + FN)
= 639 / (639 + 88)
87.9 %

Sur 727 vraies pannes, 639 ont été détectées. 88 ont été manquées — priorité à minimiser.

F1-score
2 × (P × R) / (P + R)
= 2 × 0.636 × 0.879 / 1.515
73.5 %

Moyenne harmonique de Precision et Recall. Pénalise fortement les déséquilibres entre les deux.

PR-AUC ★ métrique pivot
Aire sous la courbe
Precision — Recall
XGBoost : 0.8174

Résume la performance sur tous les seuils. Non biaisée par le déséquilibre — c'est la métrique de référence pour ce projet (remplace ROC-AUC et Accuracy).

Pourquoi PR-AUC plutôt qu'Accuracy ? Avec 3.6 % de positifs, un modèle qui prédit «OK» systématiquement obtient 96.4 % d'Accuracy et un PR-AUC de 0.036. PR-AUC punit exactement ce cas — c'est pour cela qu'il est la métrique pivot.

Compétence 3

Relier les métriques au coût métier

Les chiffres de la matrice de confusion ne sont pas symétriques — une erreur ne coûte pas la même chose selon sa nature. Cette asymétrie guide le choix de la métrique principale et du seuil de décision.

Coût modéré
Conséquence directe sur la modélisation FN >> FP en coût. On optimise donc le Recall (minimiser les pannes manquées) plutôt que la Precision ou l'Accuracy. En pratique : choisir un seuil de décision bas (ex. 0.25–0.35 au lieu de 0.5) pour détecter plus de vraies pannes, quitte à générer davantage de fausses alarmes. La courbe Precision-Recall permet de choisir ce seuil explicitement selon le ratio de coût FN/FP défini avec l'équipe métier.

Compétence 4

Plan d'expérience et note d'arbitrage

Un plan d'expérience reproductible garantit que les comparaisons entre modèles sont équitables et que les résultats ne dépendent pas de la chance ou d'un choix implicite de split.

01
Figer la métrique pivot avant tout entraînement

Choisir PR-AUC comme métrique de référence, en accord avec le coût métier. Ne pas changer de métrique après avoir vu les résultats — cela reviendrait à sélectionner la métrique qui flatte le modèle déjà entraîné.

metric_pivot = "PR-AUC" # fixé ici, non négociable
02
Définir le split temporel (pas aléatoire)

Les données de télémétrie sont des séries temporelles. Un split aléatoire crée une fuite temporelle : le modèle apprend sur des données "futures" par rapport à son jeu de validation. Utiliser le découpage 70/15/15 déjà défini dans la colonne split_set.

df_train = df[df['split_set'] == 'train'] # 70 % df_val = df[df['split_set'] == 'validation'] # 15 % df_test = df[df['split_set'] == 'test'] # 15 % — ne pas toucher avant la fin
03
Entraîner les 3 modèles dans des conditions identiques

Même pipeline preprocessing (SimpleImputer médian), même split, même random_state. Toute différence de performance doit venir de l'algorithme, pas des conditions expérimentales.

pipeline = Pipeline([ ('imputer', SimpleImputer(strategy='median')), ('model', XGBClassifier(random_state=42, ...)) ])
04
Comparer sur le jeu de validation, pas le test

Toute sélection de modèle et tout réglage d'hyperparamètre se font sur la validation. Le test reste verrouillé jusqu'à la fin — c'est lui qui valide la performance réelle. Évaluer sur le test plusieurs fois revient à optimiser pour lui.

05
Diagnostiquer l'overfitting pour chaque modèle

Calculer l'écart PR-AUC train — PR-AUC val. Un écart > 0.10 signale un overfitting significatif. Analyser les importances pour détecter une sur-dépendance à une feature unique (ex. incident_max_severity_prev_24h = 63 % du signal XGBoost TP7).

delta_overfit = pr_auc_train - pr_auc_val # > 0.10 = signal d'alarme
06
Journaliser tous les runs dans MLflow

Chaque run enregistre : paramètres, métriques, artefacts (modèle). Cela permet de comparer plusieurs expériences, de reproduire n'importe quel résultat, et de tracer l'historique pour la note d'arbitrage.

mlflow.set_experiment("maintenance_predictive") with mlflow.start_run(run_name="XGBoost_baseline"): mlflow.log_params(params) mlflow.log_metrics({'pr_auc_val': 0.8174})
